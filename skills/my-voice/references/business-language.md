# 中英文业务语言：说清生意，不表演专业

用于中文或英文报告、deck、融资 BP、创始人 pitch 的从零写作与改写。目标不是把专业内容写浅，而是让读者不必先把技术名词、抽象名词或广告腔翻译回业务含义。事实保护、派生精度和术语边界继承 `SKILL.md`。

## 一、正向表达合同

关键句优先具备这五项；原文没有的项不补造：

1. **业务主体**：客户、买家、用户、客服、财务、渠道、公司，谁在做？
2. **业务任务**：完成一笔订单、回复一张工单、核清一笔账、赢得一次续约，而不是“进行数字化建设”。
3. **动作与机制**：谁用什么输入做什么，下一步交给谁。
4. **业务结果**：使用、付费、续约、收入、成本、时间、风险；写到证据实际支持的那一步。
5. **适用边界**：时间、分母、样本、地区、渠道和尚未证明的关键结果。

先做一句测试：删掉 `平台 / 引擎 / 智能化 / robust / seamless / cutting-edge` 后，还能否看出谁得到什么？如果不能，缺的是业务含义，不是更高级的词。

## 二、中文：短主语、真动作、业务落点

### 句式

- 主语尽量具体，动词靠前。一个句子主要讲清一层关系，长定语链拆成两句。
- 把名词化空动词还原成动作：`实现对账效率的提升` → `减少找差异和查原因的时间`。没有实测结果时，只说产品做什么，不顺势写成“节省多少人天”。
- 把技术实现放到业务动作之后：`财务上传 ERP 表和银行流水，系统标出差异并给出可能原因；财务复核后处理。`
- 不把内部黑话翻译成另一套黑话：`闭环` 不能换成 `全链路`，`抓手` 不能换成 `着力点`。直接写实际步骤、负责人或结果。
- 正式材料不必强行口语化。`留存、履约、毛利、续约、增量归因` 等行业术语在读者理解且有统一口径时保留。

### 业务关系的准确说法

| 含混或技术优先 | 更清楚的写法 | 边界 |
| --- | --- | --- |
| AI 赋能客服 | AI 生成回复草稿，客服审核后发送 | 有自动发送能力才可写“自动回复” |
| 多智能体协同完成研究 | 一个步骤找资料，一个步骤核来源，人决定采用哪些结论 | 只在流程确实如此时写 |
| 打造财务基础设施 | 先帮跨境电商财务核清对账差异 | 未证明扩展前不写“基础设施” |
| 构建数据壁垒 | 积累经客户授权的差异类型、处理结果和评测数据 | 数据规模与效果未知时不称已有壁垒 |
| 提升商业化能力 | 测试谁愿意付、付多少、为何续费 | 分别对应定价与留存，不混成口号 |
| 获得市场验证 | 写实际发生的试用、持续使用、付费或续约 | 访谈兴趣不等于付费验证 |
| 采用加深 / 价值显现 | 活跃和付费团队连续两月一起增长 | 只有数据确实支持该关系时才能这样写 |

### 去翻译腔

- `基于 X，通过 Y 实现 Z`：先写 Z 是什么，再必要时写 X/Y。
- `对于……而言 / 在……方面 / 围绕……进行`：删掉不承担事实的框架。
- `被称为 / 被广泛采用 / 得到了提升`：能确认主体时改主动；不能确认时不编主体。
- 中文句中不夹完整英文短语装专业。产品名、协议名和投资人熟悉的缩写保留，首次出现时按读者需要解释。

## 三、英文：像创始人谈业务，不像生成器模仿 VC

### 句法与语气

- 默认用清楚的 sentence case 和主动语态。标题优先一个可验证判断或事实，不写两三段式标签：`Operator-Led. Clear-Eyed. Built to Win.` 没有业务信息。
- 当前事实用现在时，已完成动作用过去时，未来计划明确写成 `We plan to…`、`Our next milestone is…` 或 `The goal is…`。不把目标写成 `We will…` 的确定承诺，除非用户确实要这样承诺。
- **原稿中的广告语、最高级和宏大定位不是事实。** 即使用户要求 `keep every fact`，也不因此保留 `operating system for X / redefine the future / uniquely positioned`。只有用户明确要保留愿景时才单列 `Vision`，写清长期方向，不把它当当前能力，也不让它挤掉团队或下一验证页。
- 用具体名词：`stores / agents / tickets / buyers / finance teams / renewals`，不要所有对象都叫 `users / stakeholders / customers`。
- 用常见动词：`draft / approve / send / pay / renew / reconcile / sell / reduce / measure`。`leverage / utilize / empower / spearhead / catalyze` 多数只是在抬高调门。
- 一个标题只承担一个主张。数字能支持标题就放标题；样本、时间和分母放副标题或图注，不全塞进标题。
- 不为了“punchy”连续使用碎句、冒号、破折号、三连词和 `not X, but Y`。直接陈述事实通常更有力。

### 可以保留的投资术语

`ARR / MRR / retention / churn / NRR / gross margin / CAC / CAC payback / burn / runway / net burn / bookings / revenue / GMV / take rate / cohort` 在投资人读者中可以使用，但必须定义一致、口径可复算。不要把它们翻成过于日常的说法而丢掉精度，也不要用术语替代证据。

- `bookings` 不是 `revenue`，意向书两者都不是。
- `MRR × 12` 是年化运行率，不是已经实现的年度收入；一次性实施费不塞进 ARR。
- `active` 要写动作和统计窗口；`retention` 要写 cohort、分母和周/月口径。
- `GMV` 不是平台收入；`CAC` 要说明包含哪些成本以及 paid / blended。
- 早期数据不足时不硬算 LTV、长期留存或精确 run rate。

### “像 VC”但并不自然的表达

这张表按修辞动作判断，不做机械敏感词替换。字面命中但承担真实技术含义时保留。

| 伪地道或过度包装 | 问题 | 直接说法示例 |
| --- | --- | --- |
| `zero-edit acceptance` | 自造指标名，不像人口语 | `Agents accepted 38% of drafts without edits.` |
| `human gate / human quality gate` | 把简单审批说成像安全设施 | `A support agent approves every reply.` |
| `controlled automation` | 没说清谁控制哪一步 | `AI drafts the reply; the agent decides whether to send it.` |
| `traction with disciplined claims` | 在表演严谨，没增加证据 | 直接给使用、付费或留存数字，再在图注写限制 |
| `open business case` | 抽象且像咨询模板 | `Next, measure retention and willingness to pay.` |
| `Operator-Led / Clear-Eyed` | 标签替代创始人的具体经历 | `The founder ran support for a 40-person ecommerce brand.` |
| `purpose-built / native workflow` | 常用但信息量低 | 写清产品嵌入哪个工作界面、完成哪一步 |
| `seamless / robust / end-to-end` | 没有说明实际体验或覆盖范围 | 写步骤、耗时、覆盖范围或异常处理 |
| `the operating system for X` | 把远期愿景冒充当前定位 | 先说当前产品；有证据时再谈扩张方向 |
| `reimagine / revolutionize / redefine X` | 口号，没有客户结果 | 写客户现在能完成什么新动作 |
| `best-in-class / world-class / uniquely positioned` | 无来源最高级 | 给可比较的指标、客户行为或机制 |
| `platform / ecosystem / flywheel` | 可能不存在多边平台、生态或自增强机制 | 写实际参与方、资金流和复购/网络机制 |

### 常见中式英译

- `赋能`：多数直接重写主谓宾，不机械译成 `empower`。
- `落地`：按实际含义写 `launch / deploy / put into use / complete the first paid pilot`。
- `闭环`：写清从哪一步回到哪一步；没有循环就不写 `closed loop`。
- `全链路 / 端到端`：列出起点、终点和中间责任，不用 `end-to-end` 遮过去。
- `验证`：区分 `interest / usage / retention / paid demand / reproducible results`，不是一个 `validate` 包打天下。
- `护城河`：正文先写 `defensibility` 的具体来源，如授权数据、切换成本、网络效应、渠道或监管资质；只有机制成立才下结论。

### GTM 页面与证据页面的披露分工

官网、GitHub 首页和 GTM README 先讲愿景、目标用户价值、产品行动与采用理由，不用风险提示组成首屏。详细限制进入合同、能力文档或证据页；营销页保留准确链接。合成样例用「离线合成样例」等中性标签，不追加连续否定句。具体结构见 [GTM 营销材料细则](gtm.md)。

### 证据模块的限制只说一次，下一步必须具体

每个证据模块最多保留一处最重要的限制，放在图注、来源行或一条正文中；讲者备注补充追问，不在标题、要点、备注里反复罗列同一张“尚未证明”清单。产品机制与证据限制分开：`human approval` 是工作流，写一次即可，不要再在两条要点和备注里重复 `not autonomous`。

限制之后写下一步验证动作：`Next, measure resolution time, renewal, and willingness to pay.` 不要只写 `More research is needed`，也不要为了显得谨慎而删掉已经成立的早期信号。

**不用缺失清单凑页。** 页面要点不能只写 `Pricing is not known / Retention is not known / No data was supplied`。把它改成正面页面角色，例如 `Next, prove retention and willingness to pay`，要点写测试定价、追踪续费、建立自下而上市场模型、实测替代方案等具体动作。用户固定页数时，优先重排公司定义、产品机制、traction、团队、下一验证等页面角色；只有用户明确要审计缺口时才集中列 `not known / not supplied`。

### 派生数字保持原始精度

- 原材料写 `38% of 1,200`，若不知道 38% 是精确值还是四舍五入，不反推 `456 drafts`。
- `about 0.5` 不派生成 `exactly 87.5%` 的确定结果；可写 `roughly 87.5%`，并把计算口径放进备注。
- 月度、当周、累计和 cohort 数据不混算转化率或增长率；不同口径宁可分区，也不画在同一图里制造比较。
- 示例、目标、内部日志、客户自述和第三方数据用不同标签，不只靠字号大小区分。

## 四、完整示例：同一证据，中英文都不夸大

**已知事实**：Shopify 客服收件箱读取店铺政策与订单数据，生成回复草稿；客服审核每封回复后才发送。6 家 beta 商店使用 4 周，共 1,200 张工单，38% 草稿无需修改即通过审核。尚无解决时长、CSAT、成本、留存或收入证据。

**不够好的英文**：

> 38% Zero-Edit Acceptance: AI Support Drafts Clear the Human Bar
> Controlled automation. Native workflow. Traction with disciplined claims.

问题：自造术语、表演严谨、主语消失；没有说清谁在审核，也没有自然的下一步。

**推荐英文页**：

- **Title**: `Agents accepted 38% of drafts without edits`
- **Subhead**: `Six Shopify beta stores | Four weeks | 1,200 tickets`
- **Product context**: `AI drafts replies from each store’s policies and order data. A support agent approves every reply before it is sent.`
- **Evidence note**: `This measures draft acceptance—not resolution time, CSAT, cost savings, retention, or revenue.`
- **Next proof**: `Next, measure edit rates, resolution time, renewal, and willingness to pay.`
- **Speaker note**: `We started with drafting, not autonomous support. Agents still approve every reply. Over four weeks, six stores used the inbox across 1,200 tickets, and 38% of drafts passed without edits. That is an early signal of useful drafts. The next test is whether the product also improves resolution time and earns renewals.`

**推荐中文页**：

- **标题**：`客服无需修改就通过了 38% 的 AI 草稿`
- **口径**：`6 家 Shopify beta 商店｜4 周｜1,200 张工单`
- **产品说明**：`系统读取店铺政策和订单数据，生成回复；客服审核后才发送。`
- **证据边界**：`该指标只说明草稿通过情况，尚不能证明解决更快、成本更低或客户愿意续费。`
- **下一验证**：`继续测量草稿修改率、解决时长、续费和付费意愿。`

图文分工：标题只主张草稿接受这一件事；主图展示 38% 及 1,200 的分母，辅助模块讲产品流程与下一步，不把另外 62% 擅自命名成“全部需修改”或“全部 rejected”。

## 五、交付前回读

- [ ] 每个关键句的主体、动作和业务对象清楚；没有为了直白而改掉专业术语。
- [ ] 英文标题是事实或判断，不是标签拼接；正文没有自造“VC 术语”。
- [ ] 实际、推算、目标和限制分开；派生数字没有假精度。
- [ ] 同一限制没有跨标题、要点、图注和备注反复复读。
- [ ] 每个早期证据后面有下一验证，而不是一句空泛的 `more research is needed`。
- [ ] 中文和英文版本传达同一证据强度，不是英文版更夸张、中文版更保守。
