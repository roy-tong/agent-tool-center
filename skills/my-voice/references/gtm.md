# GTM 营销材料：先让人想采用，再让人能核验

用于官网、产品首页、GitHub Profile、仓库 README、发布页、 launch 文案和公开产品介绍。GTM 的任务是让用户理解愿景、认出自身价值并愿意迈出下一步，不是把合同、验收单或风险登记册搬到首屏。

## 一、主页叙事合同

先用[广告与 VC 传播研究](persuasion-research.md)确定**单一核心命题**：用户反复确认的核心价值不能被缩成相邻功能或一个小任务。再按以下顺序组织，允许合并，不要求每页都有独立区块：

1. **品牌信念与愿景**：产品希望哪种工作方式成为常态。用一句有方向感的话，不写市场最高级。
2. **目标用户价值**：谁的工作会发生什么具体变化。写他得到的选择、时间、机会、收入可能性或更清晰的责任，而不是产品内部对象。
3. **产品行动**：产品把什么输入变成什么结果，最关键的三步是什么；核心机制必须能支撑单一核心命题。
4. **采用理由**：可运行样例、真实案例、公开修复、独特方法或已有结果，选一个最有说服力的展开。
5. **品牌未来**：如果这条路走通，用户会多出什么新能力，行业会怎样改变；必须是当前产品的自然延伸。
6. **下一动作**：运行样例、查看案例、开始任务或联系产品负责人。CTA 用业务动作，不用「了解详情」。

愿景回答「为什么值得做」，当前能力回答「今天能做什么」。两者可以相邻，但不能把远期目标写成已经实现的经营结果。

## 二、披露放在承担它的地方

| 场景 | 主要内容 | 披露方式 |
| --- | --- | --- |
| 官网、GitHub 首页、GTM README | 愿景、价值、产品行动、采用理由、CTA | 样例属性用中性标签；详细限制进入能力文档链接 |
| BP、案例复盘、公开证据页 | 主张、证据、比较、学习、下一验证 | 在图注或证据模块保留必要口径，不反复复读 |
| 合同、验收单、安全与合规文档 | 权利义务、适用范围、风险、异常、责任 | 完整列出，不用营销语言省略 |

官网不用连续否定句证明严谨，不在标题、导语、按钮和每个卡片后重复风险提示。`UNKNOWN / UNPROVABLE / 尚未验证 / 不等于客户结果 / 不承诺` 不作为 GTM 首屏的叙事词汇。

合成样例写成「离线合成样例」「可重放演示」，接着讲用户能看到什么，不追加「这不能证明……」。真实客户样例与合成样例必须仍能一眼区分。

**如果删掉限制会让当前事实句变成假话，就改写事实句，而不是保留夸大句再补一条免责声明。** 例如，不写「全自动运营所有渠道，但有例外」，直接写「跨渠道持续执行」。

## 三、价值写法

- 把内部名词换成用户结果：`七节点推理链` → `看清机会、比较选项、推进决定`；`回执账本` → `知道发出去之后发生了什么`；`RuleMap` → `按供应商自己的规则重算`。
- 从一次任务扩到工作方式变化，但不虚构业务结果：可以说「让团队持续积累可复核的决定」，不能说「让收入翻倍」。
- 产品价值要有对象：产品团队、独立开发者、购买 AI 服务的业务与财务团队，不泛称「用户」「企业」「所有人」。
- 技术机制紧跟价值出现，用来解释为什么能做到，不单独占满首屏。

## 四、示例

**合同式写法**

> 复核一个产品决定。缺少证据时保持未知，不证明真实需求或市场结果。

**GTM 写法**

> **让好产品，从定量推演中长出来。** 自动采集数据、完成定量分析，再逐步推演出合理的产品定义判断，让数据驱动的产品决策成为每个团队的日常。

**合同式写法**

> 只有 Email 可无人值守，其他渠道需要监督或官方 API。

**GTM 写法**

> **你定目标，Growovo 把业务执行到底。** 从产品事实与目标到内容、渠道执行、回复跟进和结果回读，端到端交付每一步业务执行。

两种写法的差别不是后者删除事实，而是后者先完成营销任务，再把精确限制放到用户需要它的页面。

## 五、交付前回读

- 首屏能否用一句话说出愿景和目标用户价值？
- 读者是否能在 10 秒内明白产品做什么、为什么值得试、下一步点哪里？
- 技术名词是否都在解释用户价值，而不是展示内部结构？
- 是否仍有清晰的中性样例标签和事实分层，而没有连续风险提示？
- 详细边界是否有准确链接可去，而不是被删除或隐藏？
