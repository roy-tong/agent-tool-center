# 业务型 BP 方法：证据、定位与多版式

适用：业务型 BP、产品族方案、需要用真实数据证明价值的多产品 deck、需要原生可编辑 PPTX 的管理层汇报。页面文案与图表规则继承 [deck.md](deck.md)；面向投资人的融资 BP 另读 [bp-deck.md](bp-deck.md)。本文件处理「内容为什么成立、价值怎样被证明、版式怎样服务内容」。

方法提炼自 2026-11-17 经用户认可的 OVO 产品族 BP v7；该项目的完整复盘与专有事实归档于 ovo family 项目内，不在本 skill 重复维护。

## 编辑顺序：先基线，再定位，再证据，再版式

### 1. 先锁定基线与事实源

开始前先回答：

- 哪个文件是用户说的「最新版本」？看修改时间和目录索引，不凭记忆选文件。
- 内容正本是 PPTX、HTML、`slides.json`，还是只有 live deck？没有本地文件时，先建立可复现的本地交付，不声称已有 PPTX。
- 哪些是内容正本，哪些是历史参考？历史稿只作对照。
- 哪些案例已被明确淘汰？不把淘汰的案例和说法捞回来。

先备份原内容源和讲稿，再改。保留历史是为了能解释「哪条判断变了、为什么变」。

### 2. 区分「产品核心」与「交付属性」

定位先于版式：每个产品用一句业务语言说清客户拿到什么、下一步能做什么。警惕把交付属性当核心——「可复查」「自动化」「成本看板」都是属性，核心是替客户完成哪个决定、替代哪段劳动。

检验方法：删掉「平台、引擎、闭环、自动化、端到端」等词后，还能否说清客户拿到什么？说不清就还没定位好。

### 3. 业务背景落到产品动因

每段行业或业务背景都要落到「这解释了为什么需要这个产品」，不能成为独立的行业评论。背景段的合格线：删掉产品部分，读者仍能看出它指向哪类解法；删掉背景部分，产品主张仍能站住。

## 用证据链证明价值

### 采集量不是需求证明

采集量、发送量、测试量只回答「做了什么」，不能直接证明需求、获客或收益。口径上分清：记录数不是用户数；便利样本不能外推总体；品牌提及不是市场份额。

### 页面主体：「数据 → 推论 → 产品取舍」

每个产品的价值页用三条这样的链组织，而不是堆 KPI 或形容词：

| 数据 / 行为 | 得到的推论 | 对产品决定的影响 |
| --- | --- | --- |
| （示例）用户已把视频、数据和自述交给通用 AI 工具 | 练后反馈工作流已自发存在 | 先做归档与结构化导出，接入现有工作流，而非另造入口 |

so-what 写成业务取舍的改变（「数据让先造硬件改成先验证软件」），不是「抓到很多数据，所以需求很大」。

### 证据页结构

- 顶部：3–4 个采集与判读 KPI，写清口径。
- 左侧：一张描述性图表，只表达一个关系。
- 右侧：3 条推论卡，每条都含「观察 → 产品动作」。
- 底部：一句业务结论。
- 页脚：采集批次、分析文件、采样限制；备注补充不能证明什么。

### 定量与定性分工

- 定量：数量、时间、提及、行为、价格、替代成本，回答规模与行为。
- 定性：场景叙述、替代办法、失败、反例和用户原话，解释情境与动机。
- 推理：两类材料进入同一条链：场景 → 用户 → 痛点 → 需求 → 功能 → 产品 → 商业。
- 输出：做 / 缓做 / 不做 + 论据包 + 反例 + 下一验证。缺证时交付缺口，不硬补结论。

## 人机分工与规则

### AI 与人的工作分开写

**AI 承接**：重复、规则明确的执行——生成、排队、频率与配额检查、授权渠道发布、回读、回执、结果单、异常提醒。

**人保留**：目标与授权——服务谁、允许哪些动作、哪些内容可对外、异常与争议怎么处理、继续还是停止。

不要把「AI 替代人」写成无人负责。自动化扩大的是执行能力，不自动扩大授权。

### 用规则证明「更专业」

「更像资深员工」无法验证，规则可以。列出真实执行规则（平台限制、频率上限、账号要求、授权边界），并写成页面上可检查的条目。业务结论是：**把初级员工需要重新学习的规则，变成每次执行前的检查。**「更专业」指重复执行、规则遵守与异常留痕更稳定，不宣称已实测胜过某个人。

规则页分两层：主体是平台 / 规则 / 对动作的影响；底部给四类检查——发布权限、频率与节奏、账号与授权、回读与停止。执行案例另页展示「准备 → 发送 → 回读 → 复盘」，并把「真实动作已发生」「增长效果未知」「未知读数不补成功」分开。

## 语言与口径

### 统一产品名和比较框架

全稿每个产品固定一个名字和一句话定位；都用同一框架讲（现在的做法 / 我们的做法 / 价值提升 / 下一步）。不要一处「研究服务」、一处「产品判断」、一处「能复查的结论」，让读者猜是不是同一个产品。

### 清内部隐喻

内部术语和代码词汇不进业务页，替换成业务语言：

- dogfood → 自用试跑；traction → 可核实的付费客户、收入、复购
- 对齐 → 一致；沉淀 → 积累；触达 → 联系（语境允许时）
- 代码枚举值（如 `promo=banned`）→ 具体版块禁止推广；代码文件与平台名留在来源行

「不是 X，而是 Y」只有真实决策对照时保留，多数直接写 Y。

### 六类事实标签不能混

- **实际采集**：有批次、来源、时间、数量、采样限制。
- **人工判读**：写清判读数量和范围，不把机器关键词命中当人工结论。
- **内部自用**：只能证明方法或执行链，不能说成客户成效。
- **公开合成样本**：只能证明缺陷和修复，不能算客户损失或节省。
- **示例**：为解释结构构造，必须标「非客户数据」。
- **未来判断**：不写成当前收入事实。

没有实测提升时，直接写「尚未证明获客 / 采用 / 节省」，不要用漂亮的交付量补一个 ROI。

## 版式策略

### 先写「这页要回答什么」，再选页型

| 页面任务 | 推荐页型 |
| --- | --- |
| 行业与业务变化 | 2×2 卡片或四段链 |
| 用户与购买动因 | 人物 / 触发场景卡 |
| 方法与推理 | 输入 → 推理链 → 输出 |
| 数据证明价值 | KPI + 原生图 + 推论卡 |
| 人机分工 | 双栏对照 + 规则带 |
| 平台与规则 | 规则清单 + 检查项 |
| 费用与交付 | 结构图、2×2 矩阵 |
| 公开案例 | 前后对比柱状图 + 样本边界 |
| 持续服务 | 首次 → 复用 → 下一次 |
| 商业与积累 | 三列分阶段 |

精确对照才用表格。不要为了「统一」把每页都做成三列卡片或四行表格。

### 视觉系统服务扫读

- 16:9，统一边距、标题带、内容区、来源与页脚。
- 深色封面/收束 + 浅色正文；强调色控制在 2–4 个。
- 一页一个主张；图题写结论，来源贴近图，数据标签直接标。
- 卡片高度跟着内容走，文字框必须落在卡片内。留白是组织关系，不是剩余空间。
- 一页一图为主；图旁文字解释 so-what，不重复抄图中数字。
- 原生图表可编辑，不能把截图当「可编辑 PPT」。

## 生产流程：一个内容源，多种交付物

```
项目/
├── slides.json               # 唯一内容源：标题、正文、图表数据、来源、note
├── 逐页文案与讲稿.md          # 由内容源生成
├── name.pptx                 # 原生可编辑交付
├── name.pdf                  # 同内容转发版
└── 内部/pptx/                # 构建脚本、几何审计、逐页 PNG、contact sheet
```

原则：

1. **先备份再改。** 原内容源、讲稿、旧 PPTX/PDF 都留历史，不覆盖唯一底稿。
2. **内容只改一处。** 页面、PPTX 备注、讲稿从同一内容源生成，避免「PPT 已改、讲稿还是旧的」。
3. **原生构建。** 文本框显式尺寸，图表显式数据，页面显式 16:9；不依赖自动缩字。
4. **页型由构建函数决定。** 同是表格类不应意味着全稿同一布局；按页面问题选 cards / pipeline / evidence / rules / matrix / timeline。
5. **过程文件留在内部。** 管理层拿 PPTX、PDF、讲稿；构建脚本、审计和截图默认不作为外发附件。

版面骨架、图表配方与几何审计的具体实现用 `deck-design` skill（`assets/deck_base.py`、渲染与审计流程）；PPTX 的读取抽取、转 PDF 与逐页 PNG 预览用官方 `presentations:pptx` 插件。本文只约定流程与口径。

## 交付门禁：四条线

1. **内容结构**：页数与内容源一致；每页有演讲备注；标题连读能复述论证线；每个产品有现状、做法、价值和边界；无已删除内容残留。
2. **视觉几何**：逐页渲染，先看 contact sheet 的节奏和重复，再抽查关键页；几何审计目标 0 error（出安全区、出卡片、文本溢出、压页脚、标签遮挡）；warning 要判断是否为设计选择，不为审计变绿牺牲可读性。
3. **文案与事实**：静态文案检查目标 0 WARN，HINT 逐条人工判断；核对采集口径、样本边界、案例性质，不把「研究建议」写成「客户采用」。
4. **文件与图表**：PPTX 重新打开核对页数、备注数、图表类别与值；PDF 页数与 PPTX 一致；README、索引和讲稿链接逐个点开；不存在「主交付仍在某次对话 live deck」的不可复现交付。

## 反面清单

1. 技术语言太多 → 先写谁在什么决定前遇到了什么，再写产品怎么承接。
2. 产品族只讲一个产品 → 每个产品用同一价值框架，各自有证据。
3. 定位写成交付属性 → 先写业务结论和决策价值。
4. 价值只有形容词 → 用数据推论、规则约束、公开样本证明。
5. 采集量当需求证明 → 分清记录数、用户数、采样率和人工判读。
6. 用未确认消息支撑重大决定 → 换成可追溯研究和公开来源，不恢复淘汰案例。
7. 整篇表格 / 同款卡片 → 按页面任务切换页型，原生图表承载关键对比。
8. 多版口径并存 → 最新材料为主，历史备份，单一内容源生成所有交付。
9. 示例和内部试跑当客户结果 → 直接标非客户数据、未证明获客。
10. 只有视觉通过 → 还要检查图表值、备注、讲稿同步、链接和 PDF 页数。

## 开工前的 12 问

- [ ] 最新版本是哪一个？有没有备份？
- [ ] 每个产品的核心定位能用一句业务语言说清吗？
- [ ] 为什么是现在？背景能否落到产品动因？
- [ ] 用户现在怎么解决？我们的增量是什么？
- [ ] 价值用哪条真实证据支撑？证据能推到哪一步？
- [ ] 有没有把采集量、发送量、测试量当商业结果？
- [ ] 有没有把内部自用、公开合成样本或示例当客户案例？
- [ ] 这页最适合卡片、流程、矩阵、规则清单、时间线还是原生图？
- [ ] 图表是否有单位、来源、采样限制和明确 so-what？
- [ ] 标题、产品名、交付物名称是否全稿统一？
- [ ] PPTX/PDF/讲稿是否同源，页数、备注、图表值是否一致？
- [ ] 几何审计、逐页渲染、文案检查、链接检查是否都完成？

核心只有一句：**先让证据改变产品取舍，再用最合适的页面把取舍讲清楚。**
