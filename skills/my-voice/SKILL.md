# my-voice

目标是形成用户**想要的作者风格**：对技术有自己的判断，能讲故事，也有幽默和活人感；论证仍清楚，事实仍可核查。默认服务 **BP 与 GTM 营销材料**，不把营销官网、GitHub README 或公开叙事写成合同。报告、普通 deck、融资 BP、公开文章、合同与证据文档有不同语域，不把一种格式和披露方式套到另一种场景。

GTM 先讲**为什么值得做、谁得到什么价值、产品如何做到、下一步如何开始**；愿景与当前事实分层，但不以风险提示组织首页。PPT 的丰富度来自有效证据、比较关系、图表和判断，不来自同页堆字、堆图或补齐未知数字。

## 先确定依据

写作风格按以下顺序取舍：用户本次要求与编辑反馈 → 用户明确表示喜欢或不喜欢的成稿片段 → [已确认的风格偏好](references/voice-calibration.md) → 参考作者的技法。当前站点稿件不作为用户亲笔文风语料；旧稿可提供题材、事实线索与结构候选，事实仍需核对。

目前没有用户亲笔文风样本；已有用户认可的管理层deck视觉与表达实践，见[deck 细则](references/deck.md)的「管理层与经营汇报」小节。这份 skill 给出一个可调整的创作方向，不声称已经“发现”用户本来的语气。用户反馈某段“有活人感”或“不像我”时，优先修正判断力度、节奏和叙事方式，不机械积累口癖。

只有明确用于融资或投资人沟通时，才加载融资 BP 细则；一般商业计划、内部立项和销售提案按实际格式走报告或普通 deck。融资 BP 继承 deck 的页面表达规则，但市场、团队、证据和口径由 BP 细则决定。其他任务用本页通用规则，保留用户指定格式。用户明确指定某位作者时，优先其本次要求及可用的专项 skill；my-voice 默认不主动模仿。

**REQUIRED SUB-SKILL:** 真实 PPTX 或版式重排时使用 `deck-design`。它负责设计决策、网格、主题/模板与组件契约；本 skill 负责叙事、证据与语言。实际生成、编辑与导出按 [Deck 生产架构](references/deck-production.md)执行：**新代码型 Deck 默认 Slidev，GUI/可编辑交付优先 Presenton，Marp 仅作轻量备选，python-pptx 留给存量和高度定制的原生图表管线**。`deck-scaffold` 只维护存量，不用于新项目；独立高交互网页按需使用 `impeccable`。工具不可用时明说缺口，不把大纲或 HTML 冒充用户要求的 PPTX。

已有 deck 的大规模专项去味用 `deck-humanizer`，批量文章体检用 `shuorenhua`。完整 deck 的顺序固定为：**事实账本 → 读者与场景 → 投资论点/业务主线 → 页级内容合同 → 图表与证据 → 中英文表达 → 版面制作 → 内容、渲染、几何与文件审计**。只做文案时执行到表达层；`deck-humanizer` 不替代前面的叙事和证据工作，也不得用行数上限压掉必要证据。

## 共同底线

1. **事实和身份真实。** 不编第一人称经历、采访、实测、失败或数据。区分“我做过”“我读到”“假设一个场景”“我据此判断”。关键数字标来源、时间与口径；资料不够时降级判断或标明缺口。建议预算、中间里程碑、市场企业数和财务情景也属于新增内容，不因标成“建议”就自动合理。
2. **说明谁在做什么。** 长定语链、被动句、名词化空动词能拆就拆。术语以目标读者是否认识、改成白话是否失真来判断；产品名、专业概念、接口名和引用原文保真。英文不把 `zero-edit acceptance`、`human gate` 这类新造术语误当地道投资语言。
3. **派生数字不制造假精度。** 计算值保留输入的近似程度、时间和分母；原始比例可能经过四舍五入时，不反推出看似精确的人数或金额。实际、推算、目标、run rate 和收入分别标注，不跨时间口径算增长率或转化率。
4. **把去 AI 味当诊断，不当词语封禁。** “赋能”“值得注意的是”等空话通常删除；“不是 A 而是 B”、排比、比喻和加粗只有在承载真实区分时才保留。不要为避词而改掉事实或原稿已有的有效节奏。相近句长、重复结论、每节同款收尾比单个词更值得查。
5. **改写只动必要部分。** 保留信息点、责任主体、数字、来源及用户有意选择的语气。限定条件按交付场景归位：合同与证据页完整呈现，GTM 页面提供准确链接，不在首屏反复复读。用户明确要重写时可以重组，但不能补出不存在的证据。

## 写前与交付

从零写先确定读者、要回答的问题、材料中哪些是亲历/外部/假设、希望读者带走的判断。已有稿件先找信息最扎实、最有个性的段落和最需要修的段落，再改；别把每段抛光成同一种句型。

默认只交一版成稿，保持用户输入的格式。用户要求“先标问题”时，只给最重要的问题与建议，不顺手重写全文。用户要的是实际 PPTX、PDF 或网页时，交付对应文件并完成该形态的验证；只有用户明确要大纲、文案或方案时，才以文字稿为终点。

交付前回读两遍：一遍核对事实、来源、派生数字和限定；一遍检查主线、业务语言、口语可读性与模板痕迹。完整 deck 再做标题连读和页级证据检查：每页是否只承担一个主张，图表是否真的证明该主张，限制是否只出现一次且在合适层级。只有材料缺口会直接影响成稿真实性时，才提出精确的补充问题。
